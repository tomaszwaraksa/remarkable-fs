# reMarkable Hardware, OS & Storage Internals

This document is a technical reference detailing the hardware characteristics, operating system environment, storage layout, document data models, vector stroke binary formats, and runtime quirks of the **reMarkable 2** paper tablet. It compiles the domain knowledge collected and verified during the development of `remarkable-fs`.

---

## 1. Hardware & System Architecture

### 1.1. Device Specifications
- **Processor**: NXP i.MX7 Dual (2× ARM Cortex-A7 @ 1.0 GHz).
- **RAM**: 1 GB LPDDR3.
- **Storage**: 8 GB internal eMMC flash (approx. 6.5 GB user-accessible).
- **Display**: 10.3″ monochrome digital paper display using CANVAS e-ink technology.
  - **Resolution**: 1872 × 1404 pixels.
  - **DPI**: 226 DPI.
  - **Aspect Ratio**: 3:4.
- **Digitizer**: Wacom Feel EMR technology supporting 4096 levels of pressure sensitivity and tilt detection up to 50 degrees.
- **Battery**: 3000 mAh Li-ion rechargeable battery.

### 1.2. Operating System: Codex Linux
The tablet runs **Codex**, a custom Linux distribution built on the **Yocto Project / Poky**:
- **Kernel**: Linux 5.4.x / 4.14.x LTS (armv7l).
- **Init System**: `systemd`.
- **Display Server & Shell**: The main graphical interface is a single proprietary Qt application called **`xochitl`**. It runs directly against the Linux framebuffer device (`/dev/fb0`) with zero X11 or Wayland display server overhead.
- **SSH Daemon**: `dropbear` listening on port 22.

## 2. Networking & Connectivity

### 2.1. Dual Network Interfaces

```text
Host PC <--- (USB-C Cable) ---> USB Ethernet Gadget (10.11.99.1) [Tablet]
Host PC <--- (Local Wi-Fi) ---> wlan0 (192.168.x.x / mDNS)       [Tablet]
```

1. **USB Gadget Network (`10.11.99.1`)**:
   - When connected via USB-C, the tablet presents itself as a USB Ethernet gadget interface (`rndis_host` / `cdc_ether`).
   - Static IP: The tablet assigns itself `10.11.99.1`. The host PC typically receives `10.11.99.x` via the tablet's built-in DHCP server.
   - Always enabled and bypasses any Wi-Fi power-saving sleeps.

2. **Wi-Fi Network (`wlan0`)**:
   - Resolves locally via mDNS as `remarkable.local` using Avahi.
   - Dynamic IP assigned by your local Wi-Fi router.

### 2.2. SSH over Wi-Fi (Firmware 3.22+ Changes)
Starting with reMarkable OS **v3.22**, reMarkable disabled Wi-Fi SSH listening sockets by default to conserve battery life and enhance security.
- To re-enable Wi-Fi SSH permanently, connect over USB and run:
  ```bash
  rm-ssh-over-wlan on
  ```
- This enables and starts the `dropbear-wlan.socket` systemd unit.

### 2.3. Authentication
- **User**: `root`.
- **Default Password**: Displayed on the physical tablet screen under:
  `Settings` > `Help` > `About` > `Copyrights and licenses` (scroll down to the GPL compliance section).
- **Public Key Authentication**: Keys appended to `/home/root/.ssh/authorized_keys` provide passwordless login.

## 3. Storage Hierarchy & Document Database

All user data, notebooks, annotations, and folder hierarchies are stored in a single flat directory:
```text
/home/root/.local/share/remarkable/xochitl/
```

There are **no subdirectories for user folders**. Every document and folder is uniquely identified by a UUID v4 string (e.g., `12d0e545-19d7-4348-8640-f18e4d7ee21e`).

### 3.1. File Layout for a Document or Folder

For any given UUID, reMarkable uses a cluster of companion files:

| File / Directory | Purpose | Required For |
| :--- | :--- | :--- |
| `<uuid>.metadata` | JSON file defining title, parent folder, timestamps, and document type. | All documents & folders |
| `<uuid>.content` | JSON file defining page order, page count, layout margins, and orientation. | All documents & notebooks |
| `<uuid>.pagedata` | Plaintext file containing newline-delimited background template names. | All documents & notebooks |
| `<uuid>.pdf` or `<uuid>.epub` | The underlying binary document. | Uploaded documents only |
| `<uuid>/` | Directory containing binary `.rm` pen stroke files for each page. | Documents with handwriting |
| `<uuid>.thumbnails/` | Directory containing PNG page previews generated by xochitl. | Visual previews |
| `<uuid>.highlights/` | Directory containing text highlight coordinate files. | PDF/EPUB text selections |

## 4. Document Metadata & Descriptor Formats

### 4.1. Metadata File (`<uuid>.metadata`)

Example for a document:
```json
{
    "createdTime": "1710000000000",
    "deleted": false,
    "lastModified": "1710005000000",
    "lastOpened": "1710005000000",
    "lastOpenedPage": 0,
    "metadatamodified": false,
    "modified": false,
    "new": false,
    "parent": "10d1817f-7567-4e2a-87bb-40673f0c48d5",
    "pinned": false,
    "synced": true,
    "type": "DocumentType",
    "version": 1,
    "visibleName": "Project Architecture"
}
```

Example for a folder:
```json
{
    "createdTime": "1709000000000",
    "deleted": false,
    "lastModified": "1709000000000",
    "metadatamodified": false,
    "modified": false,
    "parent": "",
    "pinned": false,
    "synced": true,
    "type": "CollectionType",
    "version": 1,
    "visibleName": "Engineering"
}
```

#### Critical Metadata Fields:
- `type`: `"DocumentType"` for files (notebooks, PDFs, EPUBs) or `"CollectionType"` for folders.
- `parent`: The UUID of the containing folder. An empty string `""` represents the root folder. `"trash"` represents items moved to the tablet's Trash bin.
- `visibleName`: The human-readable name displayed on the tablet screen.
- `modified` and `metadatamodified`: Must be set to `false` on files uploaded externally. *(See Runtime Quirks below).*

### 4.2. Content Manifest (`<uuid>.content`)

The `.content` file maps pages and defines display layout:

```json
{
    "coverPageNumber": -1,
    "dummyDocument": false,
    "extraMetadata": {},
    "fileType": "pdf",
    "fontName": "",
    "formatVersion": 1,
    "lineHeight": -1,
    "margins": 180,
    "orientation": "portrait",
    "originalPageCount": 2,
    "pageCount": 2,
    "pages": [
        "a4f89d34-71b3-4f32-8411-9a7c642e105a",
        "89104bfa-8a19-4977-941e-3f6e91cb38a1"
    ],
    "redirectionPageMap": [0, 1],
    "sizeInBytes": "420",
    "textAlignment": "justify",
    "textScale": 1
}
```

- `pages`: An array of UUIDs representing each individual page in sequential order.
- `redirectionPageMap`: Maps physical PDF pages to logical notebook page indices.

### 4.3. Page Data Template (`<uuid>.pagedata`)
A plain ASCII text file where line `N` contains the background template name for page `N`.
- For standard PDFs: a newline character `\n` per page or empty lines.
- For notebooks: template names such as `P Lines medium`, `P Grid small`, or `Blank`.

## 5. Binary Pen Stroke Format (`.rm` Files)

Handwritten pen strokes are stored in binary files inside the document's stroke folder:
```text
<uuid>/<page_uuid>.rm
```

### 5.1. File Header
The file starts with a 33-byte or 43-byte ASCII header string:
- **Version 5**: `reMarkable .lines file, version=5   `
- **Version 6**: `reMarkable .lines file, version=6   ` (introduced in firmware 3.x with CRDT tree support)

### 5.2. Binary Structure (Version 5)
Following the header, data is structured as follows:

```
[Header: 33 bytes ASCII]
[Number of Layers: uint32 little-endian]
  For each Layer:
    [Number of Strokes: uint32 little-endian]
      For each Stroke:
        [Pen Type: uint32]
        [Color: uint32] (0=Black, 1=Gray, 2=White, 3=Yellow, 4=Green, 5=Pink, 6=Blue, 7=Red)
        [Padding: uint32]
        [Base Brush Size: float32]
        [Number of Segments: uint32]
          For each Point / Segment:
            [X: float32]
            [Y: float32]
            [Speed: float32]
            [Direction / Tilt: float32]
            [Width: float32]
            [Pressure: float32]
```

### 5.3. Coordinate System & DPI Scaling
- **Native Tablet Space**: The coordinate space ranges from `0` to `1404` horizontally and `0` to `1872` vertically (or centered about `X=0` in continuous sheets).
- **Physical Resolution**: 226 dots per inch (DPI).
- **Standard Desktop PDF Space**: 72 points per inch (DPI).
- **Conversion Factor**:
  $$\text{Scale} = \frac{72}{226} \approx 0.318584 \text{ points per tablet unit}$$

When overlaying doodles on an existing PDF, the page dimensions of the PDF (e.g. standard A4: $595.28 \times 841.89$ points) must be inspected using PDF catalog dictionaries, and stroke coordinates must be aligned with the PDF's MediaBox origin.

## 6. Xochitl Runtime Behavior & Critical Traps

Understanding `xochitl`'s runtime quirks is essential for building a reliable filesystem integration:

### 6.1. The "Ghost File" Resurrection Trap (In-Memory Dirty State)
- **The Problem**: When `xochitl` is running, it keeps loaded metadata in RAM. If an uploaded document has `"modified": true` in its `.metadata` file, `xochitl` flags the document as dirty in RAM. If the user later deletes the file from disk via SFTP or FUSE, `xochitl`'s in-memory record still exists. When `xochitl` stops or restarts, its exit handler flushes dirty documents back to disk—causing deleted files to miraculously resurrect!
- **The Solution**: Every document created, uploaded, or edited by `remarkable-fs` explicitly sets:
  ```json
  "modified": false,
  "metadatamodified": false,
  "synced": true
  ```
  This tells `xochitl` that disk state matches memory, preventing unwanted memory flush restorations.

### 6.2. Systemd Start-Rate Limiting Lockout
- **The Problem**: When performing rapid file operations (e.g., uploading or deleting multiple files), restarting `xochitl` via `systemctl restart xochitl` triggers systemd's default burst rate limit:
  ```text
  Job for xochitl.service failed because start of the service was attempted too often.
  ```
  Once tripped, the tablet UI freezes or fails to restart for several minutes.
- **The Solution**: `remarkable-fs` precedes all restart commands with:
  ```bash
  systemctl reset-failed xochitl.service && systemctl --no-block restart xochitl
  ```
  This resets the restart attempt counter before requesting an asynchronous restart, ensuring the UI always refreshes cleanly.

### 6.3. File Watcher Notification
- `xochitl` uses Linux kernel `inotify` on `/home/root/.local/share/remarkable/xochitl`.
- Touching the base directory mtime (`touch /home/root/.local/share/remarkable/xochitl`) informs `xochitl`'s internal storage listeners to rescan the directory.

### 6.4. Supported File Formats
- The reMarkable operating system natively only renders **`.pdf`** and **`.epub`** document formats.
- Plain text (`.txt`), Markdown (`.md`), Microsoft Word (`.docx`), and images (`.jpg`, `.png`) are **not supported** by the tablet e-reader software. Attempting to force them into the database causes `xochitl` to crash or display corrupted placeholder cards.

## 7. Power Management & Sleep Handling

By default, the reMarkable OS enters low-power sleep mode after 20 minutes of inactivity. When asleep:
- The display freezes on the current sleep screen (or "reMarkable is sleeping").
- Wi-Fi powers down, dropping all active SSH and SFTP connections.
- The SoC enters deep sleep, drawing fractions of a milliwatt.

### Seamless On-Demand Reconnection
`remarkable-fs` is designed to be completely passive when idle:
- **No Idle Polling or Keepalive Pings**: When no user activity is occurring in the filesystem, `remarkable-fs` generates zero network traffic and runs no background timers against the tablet.
- **Stock Sleep Preserved**: The tablet sleeps normally according to its native inactivity settings, preserving full battery life.
- **Automatic Reconnection**: When the tablet is woken up (e.g. by pressing the power button) and a file or directory is accessed, `remarkable-fs` detects the connection state and reconnects automatically over Wi-Fi/USB without requiring remounting.
